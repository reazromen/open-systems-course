MQTT Topics, QoS, Sessions, and Retained State

Design MQTT message flows with explicit topic ownership, delivery expectations, and reconnect behavior.

Learning Objectives

  • Choose topic structure.
  • Compare QoS levels.
  • Handle duplicates, retained messages, and sessions.

Topics and message contracts

MQTT topics route messages but do not automatically authorize access. Design a consistent namespace that identifies device, message purpose, and schema version without putting secrets in topic names. Broker ACLs should restrict which devices can publish or subscribe to each topic.

Quality of Service

QoS 0 is at-most-once delivery, QoS 1 is at-least-once, and QoS 2 adds a protocol handshake for exactly-once delivery within its defined exchange. QoS 1 can produce duplicates, so application handlers should be idempotent when repeated commands or telemetry would cause harm.

Sessions and retained messages

Session behavior depends on the MQTT version and connection options. Retained messages store the last retained value for a topic and may be delivered to new subscribers; do not use retained state for one-time commands unless the resulting replay behavior is intentional. Specify expiry and clean-start/session settings deliberately.

Reconnect and authorization

Reconnect with bounded backoff and re-establish subscriptions as required by the selected session behavior. Treat broker authorization errors differently from transient network failures. Test duplicate delivery, broker restart, stale retained state, and loss of connectivity.

Practical Lab

  1. Design telemetry, command, and reported-state topics; document QoS, retained policy, sessions, duplicate handling, and command IDs; test reconnect and repeated delivery.

Expected result: A topic/schema table with access permissions, QoS choice, retained-message policy, session settings, duplicate handling, and command IDs.

Troubleshooting: Inspect broker ACLs and replay behavior after reconnect; test duplicate delivery and retained state rather than relying on a single successful publish.

Common Pitfall

Assuming QoS 1 means a command executes exactly once, or treating retained state as an event log.

Check Your Understanding

1. What does QoS 1 mean?

At-least-once delivery, so duplicates are possible.

2. Why make commands idempotent?

Retries should not cause unintended repeated effects.

3. What is a retained message?

The broker's stored latest message for a topic, not complete history.

Key Takeaways

  • MQTT QoS 1 may deliver duplicates; design handlers accordingly.
  • Retained messages and session settings affect replay behavior.
  • Broker ACLs must restrict publish and subscribe permissions.
