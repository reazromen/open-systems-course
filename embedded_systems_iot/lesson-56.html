Project A: Sensor-to-Cloud Telemetry Node

Build a connected sensor node that collects measurements, validates them, and publishes trustworthy telemetry.

Learning Objectives

  • Specify a measurable sensor requirement.
  • Implement sampling and telemetry.
  • Document end-to-end verification.

System requirements

Choose a sensor with known range, units, interface, warm-up behavior, and accuracy limits. Define sampling interval, acceptable error, offline behavior, and what happens when a reading is invalid. Separate raw sensor output from calibrated engineering units.

Data path

Use a bounded sampling task or timer, validate readings, timestamp them with a stated clock-quality policy, and enqueue records for networking. Keep sensor acquisition from blocking on a slow network. MQTT or HTTP is a transport choice; the telemetry schema should remain independently defined.

Verification

Test known input ranges, disconnected network, repeated reconnects, malformed sensor values, buffer exhaustion, and reboot. A dashboard screenshot is not proof of correctness; retain logs, test steps, schema examples, and the firmware revision used.

Practical Lab

  1. Build a sensor-to-cloud path with a bounded acquisition buffer, explicit units, schema version, and documented timestamp semantics. Demonstrate valid readings, invalid-sensor behavior, network loss, and reproducible test evidence.

Expected result: A documented end-to-end sensor-to-cloud path with schema, bounded buffer, invalid-reading behavior, offline behavior, and reproducible test evidence.

Troubleshooting: Test acquisition while networking is slow or offline; verify invalid readings are rejected and sampling is not blocked by publishing.

Common Pitfall

Allowing network publishing to block sensor sampling, or calling any displayed number a validated measurement.

Check Your Understanding

1. Why separate acquisition from networking?

A slow or unavailable network should not block sensor sampling.

2. What belongs in telemetry schema?

Version, measurement, value, unit, identity, and clearly defined timestamp semantics.

3. Why isn't a dashboard screenshot enough?

It does not establish reproducibility, boundary behavior, or correctness.

Key Takeaways

  • Keep sensing independent of slow network publishing.
  • Validate readings and define units and timestamp semantics.
  • Retain reproducible evidence for normal and failure cases.
