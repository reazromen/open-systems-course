Finding Concurrency Bugs

Reproduce race conditions, deadlocks, and timing-dependent failures with explicit shared-state and ownership models.

Learning Objectives

  • Recognize data races, lost updates, deadlocks, starvation, and use-after-free.
  • Use assertions, stress tests, and host tests to narrow failures.
  • Define ownership and synchronization before adding locks.

Shared state creates interleavings

A bug may appear only when contexts interleave operations. A read-modify-write sequence can lose updates even if each access looks simple. volatile does not make a compound operation atomic. Use platform-supported atomics or synchronization with documented semantics.

Different failure classes

A race depends on timing; deadlock involves progress blocked by a wait cycle; starvation occurs when work repeatedly fails to get resources; use-after-free occurs when a pointer outlives its object. These are different problems and require different evidence.

Reproduce and observe

Stress tests, controlled delays, counters, assertions, and timestamped logs can expose rare interleavings. Logging itself can change timing. Extract shared logic into host-testable code and use host sanitizers where possible, while remembering host tests do not fully model MCU interrupts or hardware.

Ownership before locking

Document which context creates, mutates, and destroys each object; whether pointers cross queues; and when lifetime ends. Add the smallest synchronization mechanism that protects the required invariant. Test error and shutdown paths, not only steady-state behavior.

Practical Lab

  1. Review a shared counter and show how two contexts can lose an increment.
  2. Draw a two-resource lock cycle and identify the deadlock.
  3. Define ownership for a buffer passed from a driver to a worker task.
  4. Create a stress-test plan with assertions, event counters, timeouts, and a repeatable failure report.

Common Pitfall

Do not add locks indiscriminately; first identify the shared invariant, ownership, and interleaving that can violate it.

Check Your Understanding

1. Why is volatile not enough?

It does not make read-modify-write operations atomic or provide general synchronization.

2. How is deadlock different from starvation?

Deadlock is a blocked wait cycle; starvation is repeated failure to receive execution or resources.

3. Can host tests prove MCU concurrency is correct?

No. They help test logic, but hardware and interrupt behavior still need target validation.

Key Takeaways

  • Recognize data races, lost updates, deadlocks, starvation, and use-after-free.
  • Use assertions, stress tests, and host tests to narrow failures.
  • Define ownership and synchronization before adding locks.
