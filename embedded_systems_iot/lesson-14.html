Structs, Alignment, and Serialization

Represent related data clearly and encode it into stable byte formats for drivers, storage, and networks.

Learning Objectives

By the end of this lesson, you should be able to:

  • Use structures to group related fields.
  • Explain padding and alignment in memory layout.
  • Serialize fields explicitly rather than assuming a struct is a portable wire format.

Structures group data by meaning

A C struct groups related fields into one object, such as a sensor reading with a value, timestamp, and status. This improves readability and gives APIs a meaningful type. However, the compiler may insert padding between members or at the end so that fields meet alignment requirements.

struct reading {
    uint8_t status;
    uint32_t timestamp_ms;
    int16_t value;
};

The total size of this structure may be larger than the sum of its field widths. The exact layout depends on the implementation, ABI, alignment rules, and compiler options. Use sizeof to inspect a local build, but do not mistake that result for a portable external format.

Why raw struct bytes are not a protocol

Sending a struct directly over a network or writing it to persistent storage can expose padding bytes, compiler-specific layout, endianness, and differences in type representation. Padding can also contain unspecified data, which may leak previous memory contents. A robust protocol defines each field's width, byte order, encoding, versioning, and validity rules.

Explicit serialization

Serialization converts structured values into a specified sequence of bytes. For a 32-bit unsigned integer in big-endian order, the most significant byte is written first. A decoder reverses the operation and must check that enough input bytes exist before reading. For signed numbers, define the wire representation explicitly rather than relying on an undocumented cast.

// Example: encode a uint32_t in big-endian order
void put_u32_be(uint8_t out[4], uint32_t v)
{
    out[0] = (uint8_t)(v >> 24);
    out[1] = (uint8_t)(v >> 16);
    out[2] = (uint8_t)(v >> 8);
    out[3] = (uint8_t)v;
}

Production code should pair this with a decoder, explicit bounds checks, and tests using known byte sequences.

Version and validate data

Persistent settings and telemetry formats outlive a single firmware build. Include a format version or a clearly specified schema, define how unknown fields are handled, and reject malformed lengths or out-of-range values. Avoid reading a new struct layout directly from bytes written by an older firmware version unless the format was intentionally designed to be stable.

Practical Lab

  1. Define a reading structure with status, timestamp, and sensor value.
  2. Print sizeof and offsetof values on your host compiler and explain why padding may exist.
  3. Write a byte encoder for a fixed-width timestamp with a documented byte order.
  4. Test the output against a known expected byte sequence.
  5. Write a decoder that rejects truncated input instead of reading past the buffer.

Common Pitfall

Treating a compiler's in-memory struct layout as a stable network or storage format. Serialize fields explicitly and define versioning, byte order, and validation.

Check Your Understanding

1. Why can sizeof(struct) exceed the sum of field sizes?

The compiler can insert padding to satisfy alignment requirements.

2. Why is sending raw struct memory across a network risky?

Padding, byte order, type representation, and layout can vary, and padding may expose unintended bytes.

3. What should a robust decoder do with a truncated message?

Reject it safely after checking the available length; it must not read beyond the provided buffer.

Key Takeaways

  • Use structures to group related fields.
  • Explain padding and alignment in memory layout.
  • Serialize fields explicitly rather than assuming a struct is a portable wire format.
