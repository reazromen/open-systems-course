Pointers, Arrays, and Memory Layout

Understand how C accesses memory so you can reason about buffers, driver interfaces, and data ownership.

Learning Objectives

By the end of this lesson, you should be able to:

  • Explain the relationship between arrays and pointers in common expressions.
  • Distinguish object storage, pointer values, and buffer length.
  • Recognize out-of-bounds access, lifetime errors, and unsafe pointer assumptions.

A pointer is an address-bearing value

A pointer stores a location used to access an object or function. The expression *ptr dereferences a pointer to access the object it points to, while &object obtains an object's address. A pointer does not automatically carry the size of the object or prove that the address is valid.

Arrays and pointers are related but not identical

An array reserves storage for a sequence of elements. In many expressions, an array expression is converted to a pointer to its first element, but an array itself is not a pointer variable. Inside a function parameter declaration, an array parameter is adjusted to a pointer parameter, so the function does not learn the original array's length automatically.

void process(const uint8_t *data, size_t length)
{
    for (size_t i = 0; i < length; ++i) {
        // data[i] is valid only if the caller
        // provided at least length readable bytes.
    }
}

Interfaces that accept a buffer should make its length explicit and document whether the function reads, writes, or retains the memory after returning.

Lifetime and ownership

A pointer becomes invalid if the object it refers to no longer exists. Returning a pointer to a local stack variable is a classic lifetime bug. Retaining a pointer to a temporary buffer that a caller reuses can cause intermittent corruption. In embedded systems, asynchronous drivers and DMA make ownership especially important: a buffer must remain valid and unmodified for the duration required by the operation.

Memory layout is target-specific

Global/static objects, stack objects, heap allocations, and memory-mapped registers have different roles and lifetimes. The linker script and target memory map determine where sections live. Alignment requirements and cache behavior may matter for DMA buffers. Never infer that a pointer can be converted to an integer and back safely on every target or that every memory region is accessible to every peripheral.

Safer habits

  • Pass buffer length alongside a pointer.
  • Check length before indexing or copying.
  • Make ownership and lifetime explicit in API documentation.
  • Use const when a function should not modify input data.
  • Enable compiler warnings and use sanitizers in host-side tests where possible.

Practical Lab

Write a host-side C function that accepts a byte buffer and a length, validates the input, and computes a checksum. Test empty input, a one-byte buffer, a normal buffer, and an invalid length. Then create a deliberately unsafe version and use compiler warnings or AddressSanitizer where available to observe the failure.

Common Pitfall

Treating a pointer as if it included an array's length or guaranteed valid lifetime. In asynchronous firmware, the buffer must remain valid for as long as the driver or peripheral uses it.

Check Your Understanding

1. Does a pointer tell a function how large a buffer is?

No. The API normally needs an explicit length or another reliable way to establish the accessible extent.

2. Why is returning the address of a local variable unsafe?

The local object's lifetime ends when the function returns, so the pointer no longer refers to a live object.

3. Why does DMA make buffer ownership important?

The peripheral may continue accessing memory after the initiating function returns, so the buffer must remain valid and correctly synchronized.

Key Takeaways

  • Explain the relationship between arrays and pointers in common expressions.
  • Distinguish object storage, pointer values, and buffer length.
  • Recognize out-of-bounds access, lifetime errors, and unsafe pointer assumptions.
