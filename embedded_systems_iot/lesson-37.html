Tasks, Priorities, and Stack Sizing

Design task responsibilities and priorities while measuring stack needs and avoiding starvation.

Learning Objectives

  • Give tasks clear responsibilities and blocking behavior.
  • Understand priority, preemption, starvation, and priority inversion.
  • Validate stack size with platform-supported diagnostics.

Task boundaries

A task should have clear responsibility, inputs, outputs, and lifetime. Avoid creating a task for every function. Blocking on a queue or timed wait lets other tasks run; busy loops consume CPU and may starve lower-priority work.

Priorities are policy

A higher-priority ready task may preempt lower-priority tasks on a preemptive scheduler. Excessively high priorities can starve background work. Priority inversion occurs when a high-priority task waits for a resource held by a lower-priority task; mutex protocols can mitigate some cases.

Stack is per task

Each task needs stack space for call depth, local variables, and runtime overhead as defined by the platform. Deep recursion, large local arrays, and formatted logging can raise usage. Stack units and measurement APIs vary by SDK, so check their documented meaning.

Measure rather than guess

Start with a reasoned estimate, then exercise error paths and peak workload using supported high-water marks and overflow checks. A test validates only the paths it exercises. Keep a safety margin and repeat after major changes.

Practical Lab

  1. Write a task table with responsibility, priority rationale, blocking points, and stack estimate.
  2. Replace a busy loop with a documented blocking wait where appropriate.
  3. Use the target RTOS's stack high-water and overflow diagnostics in a safe test build.
  4. Exercise deep call paths and error logging; record measured margin.

Common Pitfall

Do not set priorities by intuition alone or assume a normal-path test proves stack safety.

Check Your Understanding

1. What can a busy loop cause?

High CPU use and starvation of other work.

2. What is priority inversion?

A high-priority task is delayed by a lower-priority task holding a needed resource.

3. How should stack size be validated?

Use documented runtime diagnostics under representative and stress workloads, with margin.

Key Takeaways

  • Give tasks clear responsibilities and blocking behavior.
  • Understand priority, preemption, starvation, and priority inversion.
  • Validate stack size with platform-supported diagnostics.
