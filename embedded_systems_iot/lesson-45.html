Partitions, OTA, Rollback, and Recovery

Design firmware updates around partition layout, image validation, rollback, and interrupted power.

Learning Objectives

  • Describe partitions.
  • Explain OTA slot switching.
  • Plan safe recovery.

Partition layout

The partition table describes where application images and data live in flash. OTA designs commonly reserve space for more than one application slot and track which image should boot next. Confirm that the actual partition table and flash size support the intended image; do not assume a default layout fits every product.

Update state machine

A robust update flow downloads to an inactive slot, validates the image, marks it for boot, and confirms successful startup before treating it as permanent. Handle interrupted downloads, insufficient space, invalid images, and power loss at every transition.

Rollback and recovery

Define what counts as a healthy boot and how the device returns to a known-good image when validation fails. Ensure recovery does not create an endless reboot/update loop. Keep a documented path for serial or physical recovery when network-based recovery is unavailable.

Security and compatibility

Transport encryption alone does not prove an image is authorized. Verify firmware authenticity using the platform's supported secure-update mechanisms, and plan compatibility with persistent data and backend APIs. Test the configured target and partition table on development hardware before a production rollout.

Practical Lab

  1. Inspect the partition table and OTA configuration; draw update state transitions; enumerate power-loss points and recovery outcomes; test rollback only on a development device with a recovery route.

Expected result: An update state diagram covering download, validation, boot selection, health confirmation, rollback, and interruption recovery.

Troubleshooting: Verify partition capacity and rollback support for the exact target; test only on a recoverable development device with a known-good image.

Common Pitfall

Testing only successful updates and assuming rollback works without testing resets and invalid images.

Check Your Understanding

1. Why write to an inactive OTA slot?

To preserve a known-good image while the candidate is written and checked.

2. When should candidate firmware be marked healthy?

After essential startup and health checks pass.

3. Name two OTA failure cases.

Power loss during writing and an invalid or non-booting image.

Key Takeaways

  • Partition layout must support the intended image and recovery design.
  • Validate an update before committing it as healthy.
  • Test interruption, rollback, and physical recovery paths.
