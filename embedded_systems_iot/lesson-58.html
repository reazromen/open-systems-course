Project C: Device Commands and Reported State

Implement authenticated device commands and report actual state separately from requested state.

Learning Objectives

  • Define command schema and authorization.
  • Implement idempotency and acknowledgements.
  • Reconcile desired and reported state.

Command contract

A command should have an identifier, target, operation, schema version, expiry or freshness rule, authorization context, and defined result. Validate lengths and allowed values before acting. Never treat arbitrary remote strings as executable commands.

Desired and reported state

Desired state describes what an operator or service wants; reported state describes what the device has actually applied. They can differ while offline, while a command is pending, or when a hardware operation fails. Report status and error reasons instead of claiming success on receipt.

Idempotency and authorization

Retries can duplicate messages. Use command IDs and a durable or bounded deduplication strategy appropriate to the risk; make operations idempotent where possible. Authenticate the sender, authorize each operation, reject stale commands, and audit sensitive actions without logging secrets.

Practical Lab

  1. Implement one low-risk command such as changing a reporting interval. Require authenticated authorization, unique command ID, expiry, acknowledgement states, and reported state; test duplicates, stale commands, and a device that is offline.

Expected result: A low-risk command implementation with authenticated authorization, expiry, deduplication, acknowledgements, and distinct desired/reported state.

Troubleshooting: Test stale, duplicated, malformed, and unauthorized commands; do not expose arbitrary shell or code execution as a device command.

Common Pitfall

Treating message receipt as command success or failing to defend against duplicate and stale commands.

Check Your Understanding

1. How does reported state differ from desired state?

Desired is requested; reported is what the device has actually applied.

2. Why use command IDs?

To identify duplicates and correlate outcomes.

3. What should be done with stale commands?

Reject them according to a documented freshness/expiry policy.

Key Takeaways

  • Authenticate and authorize each command.
  • Use IDs, expiry, and idempotency to handle retries safely.
  • Report applied state separately from requested state.
