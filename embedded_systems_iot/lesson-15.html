volatile, Atomicity, and Shared State

Distinguish compiler-visible side effects from synchronization and design safe communication between asynchronous contexts.

Learning Objectives

By the end of this lesson, you should be able to:

  • Explain what volatile does and does not guarantee.
  • Recognize read-modify-write races and non-atomic shared access.
  • Choose appropriate synchronization between tasks, interrupts, and hardware.

volatile is not a universal concurrency fix

The C qualifier volatile tells the compiler that accesses to a volatile object are observable side effects under the language's rules, so it must not simply optimize them away as if the value never changed externally. It is commonly relevant to memory-mapped hardware registers and certain simple communication flags.

But volatile does not make a compound operation atomic, does not prevent two contexts from racing, does not automatically provide inter-thread ordering, and does not make a multi-byte access indivisible. The exact guarantees of a particular MCU and toolchain also matter.

A read-modify-write race

Imagine a task increments a shared counter while an interrupt also increments it. Each context may read the same old value, calculate a new value, and write it back. One update can be lost even if the variable is declared volatile. The same risk appears when checking and clearing flags in separate operations.

Choose synchronization by context

  • Atomic operations: useful when the required operation is supported by the language implementation and is appropriate for the target and context.
  • Critical sections or interrupt masking: can protect a short shared operation, but increase interrupt latency and must follow platform rules.
  • Queues or task notifications: often preferable for passing events from an ISR to an RTOS task, using only APIs explicitly documented as ISR-safe.
  • Mutexes: coordinate tasks, but generally must not be taken from an ISR.
  • Single-owner design: reduces shared mutable state and can simplify reasoning about buffers and peripherals.

Memory-mapped registers are a separate concern

Hardware registers may need volatile-qualified access, but register semantics still come from the reference manual. A volatile read-modify-write can still be unsafe if a register has write-one-to-clear flags or is concurrently modified by hardware. Use the vendor's supported register access or driver API when available.

Design the ownership rule first

Before adding locks, identify who owns each variable and buffer, which contexts can access it, and whether a value must be a snapshot or a stream of events. A queue can preserve event order; a single flag may intentionally coalesce repeated events. The right mechanism depends on the required behavior.

Practical Lab

Write a small concurrency design note for a button interrupt that signals a worker task. Define what the ISR is allowed to do, which API transfers the event, how repeated presses are handled, and who owns any data buffer. Then explain why declaring a shared counter volatile would not by itself prevent lost updates.

Expected result: A concurrency design note naming shared state, ownership, allowed ISR operations, the notification primitive, and failure/overflow behavior.

Troubleshooting: Check each API’s task/ISR restrictions and identify who owns the buffer while a worker or peripheral is using it.

Common Pitfall

Using volatile as a replacement for synchronization. It addresses compiler treatment of accesses, not the full set of race, atomicity, and ordering problems.

Check Your Understanding

1. Does volatile make ++counter atomic?

No. Increment is generally a read-modify-write sequence; another context can interleave unless the operation is protected or atomic by design.

2. Can a mutex normally be used inside an ISR?

No; typical RTOS mutexes can block. Use only synchronization APIs explicitly documented as safe for interrupt context.

3. What is a useful alternative to shared mutable state?

Give one context ownership of the resource and pass events or data through a documented queue or message interface.

Key Takeaways

  • Explain what volatile does and does not guarantee.
  • Recognize read-modify-write races and non-atomic shared access.
  • Choose appropriate synchronization between tasks, interrupts, and hardware.
