Project B: Fault Injection and Offline Recovery

Test a connected device under realistic failures and prove that it recovers without hiding data loss.

Learning Objectives

  • Create a fault matrix.
  • Inject network and sensor failures safely.
  • Verify bounded recovery and visible loss accounting.

Fault matrix

List each fault, injection method, expected response, recovery bound, and evidence. Include sensor disconnect, invalid readings, Wi-Fi loss, DNS failure, broker/server outage, queue saturation, reset, and interrupted update. Avoid fault injection that can damage hardware or erase the only recoverable image.

Recovery behavior

Retries should be bounded or use backoff, state transitions should be observable, and watchdogs should detect genuine hangs rather than mask design defects. After recovery, restore sessions and reconcile buffered data. Define which data can be dropped and how the device reports that loss.

Evidence over anecdotes

Record start and end time, firmware build, fault trigger, observed state transitions, recovery duration, lost/duplicated record counts, and pass/fail criteria. Repeat tests and vary timing; one successful run does not establish reliability.

Practical Lab

  1. Write a fault-injection matrix before testing. Safely disconnect the network and sensor, simulate service outage, fill the queue, and reboot; record recovery time, dropped/duplicate records, and pass/fail against explicit bounds.

Common Pitfall

Testing only one happy-path outage and declaring recovery reliable.

Check Your Understanding

1. What belongs in a fault matrix?

Fault trigger, expected response, recovery bound, and evidence.

2. Why count dropped records?

It makes data loss visible instead of silently hiding it.

3. Does one successful run prove reliability?

No; repeat tests and vary timing and conditions.

Key Takeaways

  • Create a fault matrix.
  • Inject network and sensor failures safely.
  • Verify bounded recovery and visible loss accounting.
