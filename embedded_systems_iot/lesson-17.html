Startup Code, Vector Tables, and Linker Scripts

Understand how a microcontroller moves from reset into compiled application code and how firmware is placed in memory.

Learning Objectives

By the end of this lesson, you should be able to:

  • Describe the high-level path from reset to main or app_main.
  • Explain the role of vector tables, startup code, and linker scripts.
  • Use map files and image layout to investigate boot and memory problems.

Reset does not jump straight into your application function

After reset, a microcontroller follows a hardware-defined startup sequence. Depending on the architecture, it reads an initial stack pointer and reset handler from a vector table, enters startup code, initializes runtime state, copies initialized data to RAM, clears zero-initialized data, configures clocks or low-level hardware as required, and eventually calls application code. Frameworks such as ESP-IDF add their own bootloader and runtime initialization stages before the application's app_main() is called.

This is a conceptual sequence, not a universal instruction-by-instruction description. Cortex-M devices, Xtensa/RISC-V-based devices, ROM bootloaders, and vendor SDKs differ. Use the architecture reference manual, chip documentation, and SDK boot flow for the exact target.

Vector table and handlers

On architectures that use a vector table, entries identify the initial execution state and exception/interrupt handlers. The table's placement and format are architecture-specific. If the table or handler addresses are invalid, the processor may fault before normal application logging begins. That is why some early boot failures produce no application log at all.

What a linker script controls

The linker script describes memory regions and where sections such as code, constants, initialized data, zero-initialized data, and special metadata should be placed. The script must match the chip's memory map and the firmware framework's expectations. Placing a section in a region that does not exist, exceeds a region's capacity, or is inaccessible to a peripheral can cause link-time or runtime failure.

Flash image layout is not just a raw address

Many devices have a bootloader, partition table, application image, and optional data partitions. The flash offset for an application is a property of the board, boot configuration, partition layout, and build—not a number to copy blindly from a tutorial. Framework tools usually generate the required image list and offsets. Use those outputs and the official flashing instructions.

Diagnosing boot failures

  • Does the ROM or bootloader emit output?
  • Does the bootloader find a valid application image?
  • Does the partition layout match the built image?
  • Does the linker report section overflow or an unexpected memory placement?
  • Does the crash occur before or after runtime initialization?

A map file, ELF symbols, boot logs, and exact build configuration are often more useful than repeatedly reflashing random binaries.

Practical Lab

  1. Generate a minimal firmware build for the selected target and save the full build log.
  2. Locate the linker map file and identify the main code/data sections and memory regions.
  3. Use the SDK's documented image/flash summary to record the bootloader, partition table, application image, and offsets.
  4. Compare the result with the official board/target documentation; do not change offsets manually for this exercise.
  5. Write a boot-failure decision tree that separates ROM/bootloader, image-layout, runtime-startup, and application-level failures.

Expected result: A reproducible target firmware build with saved configuration/logs and a located linker map showing key sections and memory usage.

Troubleshooting: Confirm the exact target, SDK environment, partition configuration, and build dependencies; do not flash an image whose target or offsets are uncertain.

Common Pitfall

Treating reset, startup, linking, and flashing as invisible magic—or assuming one board's flash offsets apply to another. Boot layout must match the exact target and build configuration.

Check Your Understanding

1. What is startup code responsible for at a high level?

It establishes the runtime environment and initializes required memory and hardware state before normal application code executes.

2. What does a linker script control?

It maps program sections into memory regions according to the target memory layout and framework requirements.

3. Why should flash offsets not be copied from an unrelated example?

The bootloader, partition table, board configuration, and image layout can differ between projects and targets.

Key Takeaways

  • Describe the high-level path from reset to main or app_main.
  • Explain the role of vector tables, startup code, and linker scripts.
  • Use map files and image layout to investigate boot and memory problems.
