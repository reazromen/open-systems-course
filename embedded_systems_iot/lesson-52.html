Secure Boot, Firmware Signing, and Secret Storage

Build a chain of trust from boot verification to signed updates and protected device credentials.

Learning Objectives

  • Explain signature verification.
  • Distinguish encryption from authenticity.
  • Plan key custody and rotation.

Secure boot and chain of trust

Secure boot uses hardware and bootloader checks to restrict execution to firmware that satisfies the configured authenticity policy. The exact chain, key storage, and configuration are target-specific; follow the official documentation for the selected chip and ESP-IDF version. Secure boot does not by itself encrypt application data or prevent every runtime exploit.

Signing and key custody

Keep signing private keys out of source control, build logs, ordinary developer workstations where possible, and device firmware. Restrict signing access, maintain backups under controlled access, and document key rotation and compromise response. A checksum detects accidental changes but does not establish who authorized an image.

Secrets at rest

Store device credentials using the platform's supported protection mechanisms and limit which components can access them. Avoid hard-coded shared passwords and do not print secrets during diagnostics. Encryption at rest depends on correct key management and configuration.

Verify the configuration

Record the security configuration used to build and provision a device. Test rejection of an unauthorized image and document the recovery path before enabling irreversible production settings. Hardware behavior and available protections must be verified on the actual target.

Practical Lab

  1. Review the target's documented secure-boot/signing capabilities; write a key-custody and rotation plan; define tests for modified images and recovery access.

Expected result: A target-specific key-custody, signing, rotation, unauthorized-image rejection, and recovery plan based on official platform documentation.

Troubleshooting: Confirm capabilities for the exact chip/SDK and test in a development environment; do not enable irreversible production settings without validated recovery.

Common Pitfall

Confusing firmware encryption with signature verification or storing signing private keys in source control.

Check Your Understanding

1. What does firmware signing provide?

Authenticity and integrity evidence under the configured trust model.

2. Is encryption the same as signing?

No; encryption protects confidentiality, signatures verify authenticity/integrity.

3. Where should signing keys live?

In a controlled key-management environment, not source control.

Key Takeaways

  • Secure boot enforces a configured authenticity policy, not every security property.
  • Signing keys require strict custody and compromise planning.
  • Verify the target’s security configuration and recovery path.
