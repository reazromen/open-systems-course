BLE, HTTP APIs, and Local Device Interfaces

Choose a local connectivity interface based on discovery, power, security, and operational requirements.

Learning Objectives

  • Compare BLE and HTTP.
  • Define request and error semantics.
  • Protect local control interfaces.

Choose the interface for the job

BLE is useful for nearby provisioning or local interaction; HTTP APIs fit request/response operations; MQTT is often useful for asynchronous publish/subscribe telemetry and commands. These are design options, not interchangeable guarantees. Choose based on latency, power, network availability, security, and operational complexity.

Define API contracts

Document endpoint or characteristic names, payload schema, units, authorization, timeouts, and error responses. Validate input lengths and ranges before acting on a command. Include a schema version when the interface may evolve independently of firmware.

Local control and trust boundaries

A local interface can still be reachable by an untrusted nearby client or compromised network peer. Require pairing or authentication appropriate to the risk, authorize each operation, and avoid exposing maintenance functions without protection. Do not treat a local network as inherently trusted.

Failure and compatibility

Test malformed payloads, disconnects during an operation, duplicate requests, and unsupported versions. Define whether commands are safe to retry and return enough status for clients to distinguish rejection, timeout, and successful completion.

Practical Lab

  1. Specify a BLE or HTTP operation with authentication, limits, timeouts, and errors; test malformed and repeated requests; document what unauthorized nearby clients can do.

Expected result: An API/characteristic contract with authentication, validation, timeouts, error responses, and negative tests for malformed or repeated requests.

Troubleshooting: Test unauthenticated and unauthorized callers separately; distinguish request receipt from operation completion and make retries safe.

Common Pitfall

Assuming a local radio or LAN interface is trusted because it is nearby.

Check Your Understanding

1. When is BLE useful?

Nearby commissioning or low-power local interactions.

2. What should an HTTP API specify?

Authentication, schema, timeouts, errors, and repeated-request behavior.

3. Why is local access a security boundary?

Nearby clients may still be malicious or unauthorized.

Key Takeaways

  • Choose BLE, HTTP, or MQTT based on actual constraints.
  • Specify payloads, authorization, timeouts, and retry semantics.
  • Treat local control interfaces as security boundaries.
