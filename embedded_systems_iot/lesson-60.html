Capstone: A Documented, Testable IoT Device System

Combine sensing, secure connectivity, recovery, telemetry, and operations into a reproducible connected-device project.

Learning Objectives

  • Deliver architecture and threat model.
  • Provide reproducible build and test evidence.
  • Document recovery and maintenance.

Architecture and threat model

Document components, data flow, state machines, external dependencies, trust boundaries, assets, and likely failure modes. Include pin mappings and electrical assumptions for the exact board revision. Explain why each major design choice meets a requirement.

Reproducible build and tests

Provide source revision, target, SDK version, configuration, dependency versions, build instructions, and artifact identity. Include host tests, hardware tests, fault-injection results, and known limitations so another engineer can reproduce the evidence.

Operations and maintenance

Document provisioning, identity, telemetry, update policy, staged rollout, rollback, recovery, and decommissioning. Include sample logs and telemetry, known failure procedures, and a concise bill of materials. The capstone is complete when another person can build, test, operate, and diagnose it—not just when it boots.

Practical Lab

  1. Produce a capstone repository README with architecture diagram, bill of materials, wiring/pin table, threat model, reproducible build steps, test matrix, telemetry/command examples, OTA and recovery procedure, measurements, and limitations.

Common Pitfall

Calling the project complete because the device boots, without reproducible setup, security review, fault tests, and maintenance documentation.

Check Your Understanding

1. What makes a capstone reproducible?

Documented dependencies, target/configuration, build steps, tests, and artifact identity.

2. What operational procedures should be included?

Provisioning, updates, rollback, recovery, telemetry, and decommissioning.

3. When is the project complete?

When another engineer can build, test, operate, and diagnose it using the documentation.

Key Takeaways

  • Deliver architecture and threat model.
  • Provide reproducible build and test evidence.
  • Document recovery and maintenance.
