Flashing, Boot Modes, and the Serial Console

Flashing writes built images to nonvolatile memory; building, flashing, resetting, and monitoring are separate operations. Use the SDK-generated flash command because offsets depend on target and partition configuration. Boot straps may be sampled during reset, and sequences vary by board. Confirm the cable, port, baud rate, and exclusive serial-port ownership. Capture from power-on and identify ROM, bootloader, and application stages where possible.

Learning Objectives

  • Explain the key concepts in this lesson.
  • Apply the concepts using a small, repeatable experiment.
  • Diagnose common failures using evidence rather than guesswork.

Core Concepts

Practical Reasoning

Build for the exact target; save build and flash logs; run the generated command; capture boot output; document port recovery.

Practical Lab

  1. Copying arbitrary flash offsets or boot-button instructions from another board.

Common Pitfall

Never guess image offsets or assume boot-button sequences are universal.

Check Your Understanding

1. Why are build and flash different?

Build creates artifacts; flashing transfers them to device storage.

2. What causes garbled output?

Common causes include baud mismatch, wrong port, or configuration issues.

3. Why capture the full boot log?

It identifies the last startup stage that worked.

Key Takeaways

  • Use board-specific documentation and SDK-supported interfaces.
  • Capture logs and measurements before changing several variables.
  • Define error handling and safe recovery explicitly.
