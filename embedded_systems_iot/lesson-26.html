What Happens When an Interrupt Fires?

A timer, UART, or GPIO event sets a pending condition. When masking and priority rules permit, the CPU saves required state and runs the handler. Interrupt latency is delay until handler start; execution time is the duration of the handler. Critical sections, higher-priority events, and bus contention affect response. Keep ISRs bounded: acknowledge the source, capture essential state, and signal deferred work. Some peripherals latch one pending bit, so repeated events may collapse rather than queue.

Learning Objectives

  • Trace an event from peripheral request through interrupt handling.
  • Distinguish interrupt latency from handler execution time.
  • Identify work that must be deferred from an interrupt service routine.

Practical Reasoning

Draw the event path for a timer or GPIO; estimate event-to-handler delay; list ISR-safe APIs; document priority, acknowledgement, and deferred work.

Practical Lab

  1. Draw the path from a timer or GPIO event to its interrupt handler and identify how the peripheral signals/clears the event.
  2. Use the SDK’s documented interrupt example or a host-side timing model; do not write directly to undocumented registers.
  3. Keep the handler bounded: acknowledge the source, capture minimal state, and notify deferred work with an ISR-safe API.
  4. Record event count and response timing under a defined load; compare handler work with the deferred worker.
  5. Expected result: the event is handled without blocking APIs in the ISR; explain how pending events may coalesce or be lost for the chosen peripheral.

Troubleshooting: If events are lost or timing is unbounded, inspect the peripheral’s pending/acknowledgement semantics, interrupt masking, and queue/notification capacity.

Common Pitfall

Do not assume every event is queued or call blocking task APIs from an ISR.

Check Your Understanding

1. What determines when an interrupt runs?

Pending state, masking, priority, and architecture rules.

2. Latency versus execution time?

Latency ends when the handler begins; execution time is its duration.

3. Why keep ISRs short?

To bound interference and defer complex work.

Key Takeaways

  • Interrupt latency and handler execution time are different quantities.
  • Keep interrupt work short and defer complex processing.
  • Check peripheral-specific event-latching and acknowledgement behavior.
