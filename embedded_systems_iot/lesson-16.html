Compiler, Assembler, Linker, and Build Artifacts

Trace source code through the toolchain and learn how to make firmware builds repeatable and diagnosable.

Learning Objectives

By the end of this lesson, you should be able to:

  • Describe preprocessing, compilation, assembly, and linking.
  • Distinguish object files, ELF files, and flashed firmware images.
  • Use build output and warnings as diagnostic evidence.

Source code is only the beginning

A firmware build is a pipeline. The preprocessor expands includes and macros. The compiler translates C into target-specific intermediate representation and machine-oriented code. The assembler produces object code. The linker combines object files and libraries, resolves symbols, and places sections according to the linker script. Platform-specific tools may then generate a flashable image, add metadata, or package bootloader and partition information.

Know the artifacts

  • Source files: human-maintained C/C++ and configuration.
  • Object files: compiled code and data with unresolved symbols and relocation information.
  • ELF executable: a linked executable that commonly retains symbols and debug information useful for analysis.
  • Firmware image: a target-specific binary or packaged image intended for flashing at a specified offset or through a specific boot process.
  • Map file: a linker report showing where symbols and sections are placed and how much memory they use.

The exact filenames and packaging depend on the SDK. An ESP-IDF build, for example, produces multiple artifacts and uses target-specific tooling to prepare images and flash them at the correct offsets. Follow the official documentation for the selected IDF version and board.

Warnings are information

Warnings can reveal narrowing conversions, missing prototypes, suspicious signedness, unreachable code, or API misuse. Treat a new warning as something to understand. Do not disable warnings globally just to get a clean build; document any deliberate exception and scope it narrowly.

Reproducibility matters

Record the target, SDK version, compiler version, configuration, dependency versions, and build command. If two builds behave differently, these details help determine whether the cause is source code, a changed toolchain, a different configuration, or stale artifacts. A clean build is a useful diagnostic, but it should not be the only way the project works.

Memory reports are early warning signals

Embedded targets have fixed memory regions and image-size constraints. Linker errors and map-file growth can reveal that a new feature has consumed too much flash or RAM. Track memory changes during development instead of waiting until the final device no longer boots.

Practical Lab

  1. Create a minimal C program and build it for your host with verbose output enabled.
  2. Identify the preprocessor/compiler command, object file, linker command, and final executable.
  3. Build the same small program with debug symbols and inspect its symbols using an available tool.
  4. For ESP-IDF, create a minimal project and record the target, IDF version, build command, ELF path, binary path, and flash command reported by the build.
  5. Change one compiler option and observe which artifacts change.

Expected result: A build-stage map identifying preprocessing, compilation, assembly, linking, and the resulting object/ELF/image artifacts.

Troubleshooting: If an artifact is missing, inspect the command line, toolchain path, exit code, and build log before changing source code.

Common Pitfall

Confusing the ELF debug executable with the exact image that must be flashed, or copying flash offsets from another board/project. Use the build system's generated instructions for the exact target.

Check Your Understanding

1. What does the linker do?

It combines object files and libraries, resolves symbols, and places sections according to the target's memory layout.

2. Why keep an ELF file if the device is flashed with a binary?

The ELF commonly retains symbols and debug information that help trace addresses and diagnose crashes.

3. What makes a firmware build reproducible?

Recorded source revision, target, toolchain/SDK versions, configuration, dependencies, and build procedure.

Key Takeaways

  • Describe preprocessing, compilation, assembly, and linking.
  • Distinguish object files, ELF files, and flashed firmware images.
  • Use build output and warnings as diagnostic evidence.
