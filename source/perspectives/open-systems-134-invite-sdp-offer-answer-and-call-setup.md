A SIP INVITE does not merely say “ring this phone.”

It often carries an SDP offer describing the media session the caller can receive.

The answerer returns SDP describing the compatible session it accepts.

SIP and SDP therefore cooperate without being the same protocol.

## INVITE begins session setup

A typical call can look like:

INVITE;
100 Trying;
180 Ringing;
200 OK;
ACK.

The INVITE creates an INVITE transaction and, after final success and tags, an established dialog.

The 180 response represents ringing progress.

The 200 OK contains final acceptance.

ACK completes the INVITE handshake semantics.

## SDP is a description format

SDP describes media sessions using fields for:

origin;
session;
connection information;
media lines;
attributes.

A media line can specify:

media type;
port;
transport profile;
payload type numbers.

For audio, SDP can say which codecs and RTP parameters are offered.

RFC 8866 defines SDP.

## Offer/answer chooses compatible media

The offer/answer model is defined separately from base SDP.

Caller offers capabilities.

Callee answers with compatible choices.

The answer cannot invent a codec the offer did not make available for that media stream.

The negotiated result determines what both sides expect to send and receive.

## Payload type maps to codec meaning

An RTP payload type number does not always globally identify one codec.

Dynamic payload types are mapped through SDP attributes such as rtpmap.

For example, one call might map payload 111 to one codec while another maps it differently.

Packet analysis must read the SDP for that session.

## Direction attributes matter

SDP can declare:

sendrecv;
sendonly;
recvonly;
inactive.

These become important for hold, announcements, recording, and asymmetric media.

A call with valid RTP addresses can still have one-way media because the negotiated direction intentionally disables one direction.

## Early media can start before 200 OK

Some networks send media during provisional responses, often using 183 Session Progress with SDP.

That supports ringback tones or announcements generated by the far network.

Therefore “media starts only after answer” is not universally true.

Trace signaling and media timestamps instead of assuming.

## Re-INVITE and UPDATE can modify sessions

During a call, media parameters can change.

A re-INVITE can renegotiate codec, direction, or media address.

The UPDATE method can also modify session parameters under its rules.

Hold and resume are commonly implemented through SDP direction/address changes rather than a magical “hold packet.”

## DTMF may not be audio

Digits can be carried as audible tones inside the audio codec.

They can also use named telephone-event RTP payloads as standardized by RFC 4733.

SIP INFO is another deployed mechanism, though interoperability depends on implementation and agreement.

When DTMF fails, first determine which method is in use.

## Practical inspection

Capture one call on an authorized system.

Extract the SDP offer and answer.

Write down:

caller RTP IP/port;
callee RTP IP/port;
offered codecs;
accepted codec;
telephone-event payload;
direction attributes.

Then compare those values with the actual RTP packets.

If the packets go somewhere else, an intermediary may be rewriting or relaying media.

SIP creates signaling state; SDP negotiates media parameters.
