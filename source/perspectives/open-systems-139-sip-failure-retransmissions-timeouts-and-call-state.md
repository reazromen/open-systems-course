A user says:

the call dropped.

That is a symptom.

A useful diagnosis asks:

Which dialog?
Which side sent the terminating message?
Was there a BYE?
Did a transaction time out?
Did media fail while signaling remained alive?
Did a session timer expire?

## UDP SIP retransmits at the application layer

When SIP uses UDP, the transaction layer retransmits messages according to timers defined by SIP.

Repeated INVITEs in a packet capture can therefore be normal retransmissions, not the application repeatedly deciding to call.

Look at Via branch, CSeq, Call-ID, timing, and response state.

## 100 Trying suppresses upstream retransmission pressure

A proxy or user agent server can send 100 Trying to indicate the request is being processed.

For INVITE over UDP, this reduces continued retransmission while routing or downstream setup takes time.

Provisional responses are part of transaction progress.

## CANCEL stops a pending INVITE

If the caller hangs up before the call answers, it can send CANCEL for the pending INVITE.

CANCEL does not terminate an already established dialog.

Once the call is established, BYE is the normal method to terminate it.

Confusing CANCEL and BYE is confusing pre-answer and post-answer state.

## BYE tells you which dialog endpoint ended the call

If endpoint A sends BYE, A initiated dialog termination at the SIP layer.

The Reason header can sometimes provide additional protocol cause information.

That still may not reveal the human cause.

A PBX could generate BYE because of application policy, media timeout, trunk failure, or administrative action.

Correlate with server logs.

## No BYE can be an important clue

If media stops and no SIP BYE exists, possibilities include:

network path failure;
process crash;
power loss;
NAT mapping expiry;
media watchdog later terminating call;
capture taken at wrong boundary.

The absence of signaling evidence is itself evidence.

## Session timers detect stale dialogs

RFC 4028 defines session timers that periodically refresh SIP sessions.

If the refresher fails to update the dialog before expiry, the session can be terminated.

A call that drops at a repeatable long interval can therefore point to session-refresh failure rather than RTP quality.

Look for re-INVITE or UPDATE refresh traffic.

## 408, 480, 486, 487, and 503 mean different things

408 Request Timeout: transaction did not complete in time.

480 Temporarily Unavailable: target is currently unavailable.

486 Busy Here: endpoint indicates busy.

487 Request Terminated: request was terminated, commonly after CANCEL.

503 Service Unavailable: server cannot currently process request.

Treating all of them as “call failed” discards useful state.

## Forking creates multiple branch outcomes

One INVITE can fork toward several registered Contacts.

One branch rings.

Another returns busy.

Another times out.

One finally answers.

The upstream proxy must combine branch state into a final outcome according to SIP rules.

A trace can therefore contain several contradictory-looking responses that are all legitimate branch results.

## Media timeout is implementation policy

Many PBXs/SBCs can hang up a call after not receiving RTP for a configured interval.

That is not a core SIP timer.

It is local media-liveness policy.

When a call ends after silence, inspect both SIP and RTP and identify whether the server generated BYE due to its own media timeout.

## Practical failure drill

In a system you control, reproduce several safe cases:

callee busy;
callee unregistered;
callee rings then caller cancels;
callee answers then hangs up;
network path to one test endpoint removed.

For every call, record:

final SIP response;
which side sent CANCEL/BYE;
Call-ID;
duration;
server log reason.

Build a table mapping visible user symptom to protocol evidence.

## The lesson to carry forward

Call failures are state transitions distributed across several SIP agents and media paths.

The final telephony lesson follows one call end to end from registration through routing, SDP, RTP, NAT, trunking, and teardown.
